# 架构与可行性 — Architecture & Feasibility

> 动手前的技术决策:**可行性、稳定性、可扩展性(以后能不能随便加学习任务)、排名系统设计。**
> 配套:`FRAMEWORK.md`(产品)· `ENGAGEMENT.md`(留存)· `MONETIZATION.md`(盈利)。

---

## 1. 可行性(诚实评估)

| 维度 | 结论 | 说明 |
|------|------|------|
| **教学法** | ✅ 已验证 | Thomas's Money Adventure 证明这套关卡式教学可行。 |
| **前端技术** | ✅ 成熟 | Expo/RN 生态完备:动画 `reanimated` + `react-native-svg`;mascot 成长建议用 **Rive**(状态驱动的角色动画,天生适合"蛋→成年"多形态切换),备选 Lottie。 |
| **后端** | ✅ 地基现成 | 仓库已有 FastAPI + Postgres,账号/榜单/邮件都是标准活。 |
| **我能在 remote 建** | ✅ | node22 + npm + 能连 registry,可搭工程、写全部代码;真机用 Expo Go 测。 |

### ⚠️ 真正的风险不是代码,是**内容**

> **代码是简单的部分。把 ML / 私募 / 艺术 都做到"深且正确、还适合触屏关卡化"才是最贵的部分**,
> 需要每个领域的专业度。这决定了产品成败,也是为什么"重点是学习"(`FRAMEWORK.md` §0)。

- 对策:**一次只深做一所学院**(先 Money,已起步),做透再开下一所;别铺太广做成一寸深。
- 每门课走"专家审 + 讲回来验证"双关,保证不是"花哨但空洞"。
- 诚实:我能帮你搭出色的**框架和工具**,但每个领域内容的深度需要你/领域专家把关——我不会假装能一个人把私募和艺术都做到专家级。

## 2. 稳定性

- **离线优先(offline-first):** 关卡能离线玩,联网只做同步。网络抖动不影响学习,稳。
- **本地优先 + 云同步:** 进度先写设备(AsyncStorage),再同步服务器。单设备可用,多设备一致。
- **内容热更新(关键):** 课程是**数据**,通过 **Expo Updates(OTA)** 推送内容/修 bug,**不必每次都过 App Store 审核**。改个错字、调个数值当天上线。
- **简单状态管理:** Zustand 或 Context,不引入 Redux(也符合仓库既有约定)。
- **防御性:** 端上不可信(XP 服务端校验)、错误集中处理、关键路径有测试。

## 3. 可扩展性 —— 命门:**内容即数据(Content-as-Data)**

> 你问"架构能不能以后随便加别的学习任务"。**能,但前提是现在就把课程设计成数据,而不是代码。**
> 这是整个工程最重要的一个决定。

### 怎么做

把一门课拆成**声明式的数据树**,app 是"播放器",内容是"片子":

```
School → Track → Chapter → Mission → [Step...]
                              每个 Step 有一个 type,app 按 type 渲染对应组件
```

**Mission Step 的类型库(可复用的"积木"):**

| type | 交互 | 例子(来自 Thomas 课) |
|------|------|----------------------|
| `info` | 一屏讲解 + 动画 | "投资就是让钱长大" |
| `slider-sim` | 拖滑块看结果 | Snowball Machine(复利) |
| `choice` | 点选 | Spend/Save/Plant |
| `drag-match` | 拖拽配对 | 把术语连到定义 |
| `tap-game` | 限时点击 | Trading 抢买卖 |
| `quiz` | 测验 + 即时反馈 | The Big Money Quiz |
| `explain-back` | 让用户复述(可录音/选句) | "用一句话讲给别人听" |

- **加一门新课 = 写一份新数据(JSON/schema),不改 app。** ML、艺术、私募全套这套积木。
- **加一种新玩法 = 加一个 type 的渲染组件**(一次性工程),之后所有课都能用。
- **mascot 注册表:** 动物是配置项(`{domain, animal, stages, rig}`),加动物=加一条配置。
- **强类型 schema:** 用 TypeScript 类型 + 运行时校验(zod),保证数据正确,坏数据进不来。

> 这套设计直接满足你的诉求:**今天做理财,明天加 LLM,后天加艺术——都是加数据,架构不动。**

## 4. 排名系统设计(回答:每周一次?每周重置?)

### 学习是**每天**,排名是**每周**——别搞混

- **学习节奏:目标是每天一点点**(信念 #5)。不要做成"每周才学一次"——那样养不成习惯。
- **比赛节奏:每周联赛 + 周一重置。** 一个 7 天窗口累计 XP 排名。

### 为什么是"每周 + 重置"

- **周一重置 = 每周一次 fresh start**:上周垫底也能东山再起,没有"永远追不上"的绝望(对孩子尤其重要)。
- 7 天:比每日稳(不被一天波动主导)、比每月快(总有近在眼前的目标)。
- **重置的只是"比赛排名",不是你的成长**:XP 总量、mascot 成熟度、badge、streak **永久累积,永不清零**。重置的是竞技场,不是你养的动物。

### 怎么排

- **小组联赛**(15–30 人/组)+ **升降级**(Bronze→…→Diamond),按上周活跃度配对(详见 `ENGAGEMENT.md` §4)。
- **多榜并存:** 周榜(竞技)+ 好友榜(关系)+ 个人最好(和自己比,可作唯一榜给不爱竞争的人/孩子)。
- **防刷分:** XP 服务端结算,端上只是显示。

## 5. 技术栈一览(建议)

| 层 | 选型 | 理由 |
|----|------|------|
| App | **Expo / React Native (TypeScript)** | 一套码 iOS+Android 触屏;OTA 热更新 |
| 动画 | **Rive**(mascot)+ reanimated + svg + Lottie | 状态驱动角色成长 / 流畅交互 |
| 端上存储 | AsyncStorage(+ SQLite 备选) | 离线优先 |
| 状态 | Zustand / Context | 简单,无 Redux |
| 后端 | **FastAPI + Postgres**(复用仓库现有) | 账号/榜单/同步 |
| 认证 | Expo Auth / 第三方(Apple/Google 登录) | 触屏少打字,社交登录优先 |
| 推送 | Expo Push(+ 本地通知) | 原生可靠 |
| 邮件 | Resend / Postmark | 每周召回邮件 |
| 内容 | 声明式 JSON + zod 校验 + Expo Updates | 内容即数据 + 热更新 |

---

## 6. 一句话总结

**可行、可稳、可扩——只要现在把"内容即数据 + 离线优先 + 热更新"这三件事设计对。**
真正的长期成本和护城河都在**内容深度**,不在代码。
